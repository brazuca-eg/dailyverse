# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

Dailyverse is a small collection of daily games, in the spirit of magnitudle.com. One puzzle per game per day, the same for everyone, playable in under two minutes.

First game: **Mystery Place**. The player guesses a country from five progressively more specific clues. Every wrong guess unlocks the next clue and shows distance and compass direction to the answer. Score is 5 points for a first-guess win down to 1, and 0 for a loss.

Stack: Astro 7 (static), React 19 islands, TypeScript strict, Vite, Vitest 5. No backend and no database: puzzles are JSON, player state is `localStorage`.

## Architecture

```
src/
  core/            Game-agnostic logic: countries, distance, daily index, guessing rules, game storage, share text, streak, random, difficulty, search, text, clipboard
  hooks/           Game-agnostic React hooks: useGuessingSession, useHelpDialog, useTodaysItem
  games/<game>/    One folder per game. Its own data, rules and stage component; the shared GuessingGame composes the rest
  ui/              Shared components: GuessingGame (the whole country-guessing screen), GuessInput, GuessHistory, ProgressPips, ResultPanel, RulesPanel, Modal, ShareButton, NextPuzzleCountdown, StatsSummary, icons
  layouts/         Astro layouts
  pages/           Astro routes; each game page mounts one island with client:only="react"
  styles/          Global CSS: tokens, base, animations, primitives, home
  testing/         Vitest setup (jsdom dialog polyfill, cleanup)
scripts/content/   Puzzle drafting and verification pipeline (tsx CLI)
content/           Drafts and the content README
```

Rules of placement:

- Game-agnostic code goes in `core/`, `hooks/` or `ui/`. Nothing in them may import from `games/`, and one game never imports from another.
- A new game gets its own `src/games/<name>/` folder and its own page. Reuse `core/` and `ui/` before writing anything new.
- Pure logic lives in `.ts` files with no React. Components only render and wire.
- Stateful behaviour lives in hooks (`useGameSession`, `useTodaysPuzzle`, `useHelpDialog`), not inside components.

### Daily puzzle

`puzzles[daysSinceLaunch % puzzles.length]`, using the UTC day. The index is computed once on mount, so a session that crosses midnight keeps its puzzle. `launchDate` is a placeholder until the real launch.

### Persistence

Each game creates its storage with `createGameStorage("<game>")` (`core/gameStorage.ts`), which uses the keys `dailyverse:<game>:game`, `:stats`, `:help-seen`. Reads go through `core/storage.ts`, which tolerates a missing or blocked `localStorage` and corrupt values. Saved game state is validated against the current puzzle and day before use. Never read or write `localStorage` directly from a component.

### Games

- **Mystery Place** (`games/mystery-place`): five clues from a hand-checked JSON list.
- **Flag Fragment** (`games/flag-fragment`): guess the country from a flag that zooms out after each wrong guess (crop, bigger crop, blurred, greyscale, full). Flag SVGs come from the `flag-icons` package. `flags.json` holds a difficulty and a crop focus per country and is generated by `npm run flags:generate` from the lists in `scripts/flags/difficulty.ts`. The daily order is a seeded shuffle (`schedule.ts`) that follows the weekly easy/medium/hard pattern.
- **Spot the Difference** (`games/spot-difference`): two generated SVG outdoor scenes with 5 differences (removed, moved, resized, reshaded or reshaped elements), 3 lives. `generateScene(seed)` builds a deterministic scene, `planDifferences` alters 5 elements by tier (easy/medium/hard follow the weekly pattern), and the daily puzzle is `buildDailyPuzzle(dayIndex)` (seed = day + 1000). The UI draws scenes with the same `renderSceneContent` that the verifier rasterises. After changing any rule in `scenes`, `differences`, `elements` or `difficulty`, run `npm run spotdiff:verify -- 0 400`; it pixel-checks that every changed pixel lies in a declared difference area and that each has at least 25 visible pixels. Each picture is a real `<button>`: Tab to focus, arrow keys move a crosshair (Shift for small steps), Enter or Space marks; a Zoom button enlarges both pictures with synced scrolling, and the tap tolerance widens on small screens so a fingertip can hit.
- **Tents and Trees** (`games/tents-trees`): a daily logic puzzle, 6x6, 8x8 or 10x10 by the weekly tier. A tent next to every tree (one each), no two tents touching, row and column counts met. `generateTentsPuzzle(seed, tier)` places tents, adds a tree beside each, and keeps a puzzle only if `solve` finds exactly one solution and `solveByLogic` (sound rules plus one-step lookahead) solves it with the tier's lookahead count. Because every logic step is sound, a logic-solved puzzle is unique; the exhaustive `solve` is an independent cross-check. The daily round is `buildDailyRound(dayIndex)` (seed = day + 2000). After changing a rule, tier setting or the generator, run `npm run tents:verify -- 0 400`. The board is a native table with `role="grid"`: tap cycles tent, grass, empty; dragging paints grass; arrow keys, Enter or Space, G and Backspace work from the keyboard. Check and Hint each cost a point; time is shown but not scored.
- **Trail Words** (`games/trail-words`, finished): a Spelling Bee style game with seven letters, a centre letter and a pangram, medium and hard days only. Data comes from `npm run words:build`, which downloads SCOWL (common = size 50, accepted = size 70), the public-domain ENABLE list (words must also be in it, which removes abbreviations) and the LDNOOBW blocklist into `.cache/trail-words/`, then writes `words.txt` (a notice header, then one word per line, common words ending in `*`) and `puzzles.json` (one code per puzzle: centre letter first, then the six others). Run `npm run words:verify` after every build; it re-checks the notice, blocklist, tier rules, duplicates and pool sizes. The blocklist cannot prove that no objectionable word remains, so add anything you find to `EXTRA_BLOCKED` in `filter.ts`. The licence notices live in `content/trail-words/NOTICE.md` and at the top of `words.txt`; keep them. The puzzle engine: `daily.ts` picks the day's puzzle (weekly pattern medium, hard, medium, medium, hard, medium, hard; each tier walks its own seeded shuffle of its pool, from `TRAIL_LAUNCH_DATE`), `puzzle.ts` builds the word list for a code, `ranks.ts` has the ranks (win at Ranger, half the common-word score), `hints.ts` counts remaining words by first letter and length, and `wordList.ts` lazy-loads `words.txt` so only this page pays for it. `npm run trail:verify -- 0 730` checks every day of a range against the tier rules. The game logic: `game.ts` holds the saved state (`puzzleId`, found words, `ended`), guess validation with one reason per rejection, score and status (won as soon as Ranger is reached, play can continue; lost only when the player ends the game early), typing helpers and the feedback messages; `persistence.ts` stores it under `trail-words`; `share.ts` builds the spoiler-free share text. The UI: `TrailWordsGame.tsx` shows the honeycomb at once from the puzzle code (disabled) while the word list lazy-loads, then mounts `TrailPlay`; `useTrailSession.ts` owns input, toasts, shuffle, saved state and stats (it keeps the latest input in a ref, because keys can arrive faster than React renders); `useTrailKeyboard.ts` handles the physical keyboard and steps aside for dialogs, text fields and focused buttons. Components: `Honeycomb`, `WordInput`, `RankBar`, `FoundWords`, `HintPanel`, `TrailControls`, `TrailResult`. The centre hex uses `--on-accent` on `--accent` (contrast-tested). Performance: the page script in `trail-words.astro` starts the dictionary download immediately, in parallel with React hydration (measured on a production build: the request now starts at about 40 ms instead of 100 ms); the dictionary chunk is about 183 KB gzipped (147 KB brotli) and only this page loads it; a submitted word takes about 5 ms to reach the screen. Contrast pairs used by this game are in `src/styles/contrast.test.ts`.
- **Peak Order** (`games/peak-order`, finished): put 5 mountains, rivers, lakes, islands or volcanoes in order of height, length or area. Data comes from `npm run peak:build`, which queries Wikidata (CC0, see `content/peak-order/NOTICE.md`) into `.cache/peak-order/` (delete it to refresh) and writes `puzzles.json`: per category a list of `[name, value, editions]` items (only those puzzles use, sorted by value) plus `medium` and `hard` pools of index sets and the popularity cut-off used. Fame is the number of Wikipedia editions excluding Cebuano, Swedish and Waray (bot-written); medium uses a category's 100 best-known items (gaps of at least 15% between neighbours), hard the best 250 with a closest pair 3-8% apart. Pools are 90 medium and 70 hard puzzles per category, each item used at most 8 times. Run `npm run peak:verify` after every build; it re-checks names, values, pool sizes, tier rules and duplicates. Waterfalls, national parks and deserts were tried and dropped (too few well-known items, ambiguous labels). The engine: `daily.ts` picks the day (category rotates daily over 5 categories, tier follows the weekly pattern medium, hard, medium, medium, hard, medium, hard, so the schedule repeats every 35 days; each pool walks its own seeded shuffle from `PEAK_LAUNCH_DATE`), `puzzle.ts` builds the five items (ascending by value) and a seeded start order with at most one item already in place (`arrange.ts`), `arrange.ts` also has `moveItem` (insert semantics, used by tap-to-place and the up/down buttons), and `feedback.ts` marks each position right or wrong. `npm run peak:verify-days -- 0 730` checks every day of a range. The game logic: `game.ts` holds the saved state (`puzzleId`, current `order`, and `history` of the orders that were checked; everything else is derived), with 5 checks, status (won on any right check, lost after 5 wrong ones), `canCheck` (false when the order has not changed since the last check, so a check is never wasted), `applyMove`, `applyCheck`, `readConfirmed` (a green mark from the last check stays only while its item has not moved) and the score (5 for a first-check win down to 1, 0 for a loss); `persistence.ts` validates and stores it under `peak-order`; `share.ts` builds the spoiler-free share text (one row of green and white squares per check); `format.ts` has `formatValue` (thousands separators and unit) and `buildPrompt`. The UI: `PeakOrderGame.tsx` builds the day's puzzle synchronously (the data is bundled, about 18 KB gzipped) and mounts `PeakPlay`; `usePeakSession.ts` owns selection, moves, checks, notices, saved state and stats, and asks the list to move focus after a keyboard or button move (`focusRequest`, because React re-orders the DOM nodes); `PeakList.tsx` is the ordered list. Rows are real buttons: tap one then tap where it goes, Enter then arrow keys, Escape to let go, up and down buttons per row (44px targets), or HTML5 drag and drop (the drag source is kept in a ref, so text dragged in from elsewhere is ignored). After the game the rows become plain text with the real values; on a loss they show the right order. `PeakList.tsx` has an ESLint override for the draggable list items; every drag action also has a button or keyboard equivalent. Checked on a production build: the game chunk is 22 KB gzipped (19 KB brotli, of which about 18 KB gzipped is the puzzle data), it starts loading at about 25 ms with no waterfall because the data is bundled, a move takes about 2 ms, and at 320px wide there is no horizontal scroll, long names wrap, and the up and down buttons are 44x44. Touch dragging was not tested on a real phone; tap-to-place and the buttons cover touch.
- **Trail Sudoku** (`games/trail-sudoku`, finished): a daily Sudoku. Easy and medium days are 6x6 (2x3 boxes), hard days 9x9, following the weekly easy/medium/hard pattern (`core/difficulty`). Puzzles are pre-generated into `puzzles.json` (strings of digits, 0 = empty; 210 easy, 315 medium, 210 hard, so two years without a repeat) by `npm run sudoku:build` (about 50 s; seeds are fixed per tier and pool index, so a bigger pool keeps the old puzzles, and published puzzles stay stable if the generator changes). Run `npm run sudoku:verify` after every build (about 20 s): a brute-force `countSolutions` proves exactly one solution, and `solveByLogic` must solve it within the tier's technique levels. Technique levels in `logic.ts`: 1 naked single, 2 hidden single, 3 locked candidates and naked pairs, 4 hidden pairs and naked triples (`TECHNIQUES`, injectable so tests can switch one off; every technique has a real puzzle that needs it). Tiers (`tiers.ts`): easy = naked singles only with at least 18 clues, medium = needs hidden singles (sparse, about 9-11 clues), hard = 9x9 needing level 3 or 4. The daily pick (`daily.ts`) walks a seeded shuffle of the tier's pool from `SUDOKU_LAUNCH_DATE`; the solution is not stored but solved at runtime (`solveGrid`, a few ms). Game logic (`game.ts`): state holds the player's `entries` (givens are never copied in), pencil `notes` as bit masks, `flagged` squares from the last check, `moves` for undo, checks, hints and elapsed time; entering the same digit again clears it; Check marks wrong squares and costs a point only when it finds some (as in Tents and Trees); Hint fills the selected square (or the first one that needs help) and costs a point; score is 5 minus checks and hints, at least 1 for a solve and 0 for giving up. Rule clashes are marked instantly by `findConflicts`. UI: `SudokuGame.tsx`, `useSudokuSession.ts` (timer, selection, notes mode, stats), `Board.tsx` (a `role="grid"` table of buttons with a roving tabindex; arrows, 1-9, Backspace/Delete/0, N for notes, U for undo) and `NumberPad.tsx` (digit keys show how many are left and disable at zero). Selection and notes mode are also read from refs, because keys can arrive before React re-renders. Notes are not auto-removed when a digit is placed. On a 320px phone the nine number keys are about 28px wide and the 9x9 squares 30px (the keys are 52px tall); Sudoku apps do the same. The elapsed-time formatter moved to `core/elapsed.ts` (shared with Tents and Trees), and the daily pick uses `core/dailyPool.ts`.
- **Switchback** (`games/switchback`, finished): a Zip-style path puzzle. Draw one trail from checkpoint 1 through the numbered checkpoints in order, covering every square exactly once; fences (blocked borders between squares) appear on medium and hard days. Tiers follow the weekly easy/medium/hard pattern: easy 5x5 with 5-8 checkpoints and no fences, medium 6x6 with 4-6 checkpoints and 3-8 fences, hard 7x7 with 4-5 checkpoints and 7-12 fences (`tiers.ts`, enforced by the generator and `npm run switchback:verify`). Puzzles are pre-generated into `puzzles.json` (`{ m: marks, w: flat fence pairs }`; 210 easy, 315 medium, 210 hard) by `npm run switchback:build` (about 40 s, fixed seeds per tier and index). Generation (`generator.ts`): `pathgen.ts` makes a random Hamiltonian path by backbiting (repeatedly reversing a segment from an end, starting from a serpentine), then the generator adds constraints until the solver finds exactly one solution (each time it picks a second solution and adds a checkpoint or a fence that rules it out), then removes every constraint that is not needed. `solver.ts` is a backtracking search with connectivity and dead-end pruning; the last checkpoint may only be entered when every other square is covered (that rule is also enforced in `game.ts`). The daily pick uses the shared `core/dailyPool.ts` (also used by Trail Sudoku, so both keep two years without a repeat). Game logic (`game.ts`): state is just the `path` (plus hints, time, status); `moveTo` extends the trail, steps back onto the previous square, or cuts the trail back to any earlier square; Hint cuts the trail back to where it still agrees with the solution and adds the next right step (costs a point); score is 5 minus hints, at least 1 for a solve, 0 for giving up. UI: `Board.tsx` draws squares as buttons with an SVG overlay for the trail (a dashed footpath), fences and the hiker marker; pointer dragging uses `elementFromPoint` (touch-action none), a click only moves when it came from the keyboard (`detail === 0`), arrow keys step the trail and keep focus on its end, Backspace undoes and R resets; `useSwitchbackSession.ts` reads the latest trail from a ref so rapid steps work. Fences are drawn in `--text` so they stay readable on every tile in both themes. `Board.tsx` has an ESLint override for the wrapper that handles pointer and key events (every square is a real button).
- **Bear Sweeper** (`games/bear-sweeper`, finished): a minesweeper that never needs a guess. Bears hide in a grid; a revealed number counts the bears in the 8 squares around it; the clearing around the start square is already open. Tiers follow the weekly easy/medium/hard pattern: easy 7x7 with 8 bears (single-square rules), medium 9x9 with 15 bears (needs the subset rule), hard 11x11 with 24 bears (needs the global bear count or the one-step what-if), see `tiers.ts`. Puzzles are pre-generated into `puzzles.json` (`{ b: bears, s: start }`; 210 easy, 315 medium, 210 hard) by `npm run bears:build` (about 3 s, fixed seeds per tier and index); run `npm run bears:verify` after every build. The no-guess guarantee is the solver: `logic.ts` simulates a player who only uses sound deductions (technique levels: 1 single-square rule, 2 subset rule over two numbers, 3 global bear count and a one-step lookahead that assumes a square is a bear or safe and looks for a contradiction); a generated layout is kept only if the solver finishes the whole board within the tier's level and reports zero `mistakes` (any deduction that disagrees with the real bears). `TECHNIQUES` is injectable, so tests switch one off and use real pool puzzles that need it. Bears are never placed in or next to the start square, so the start is a blank square that opens a clearing (`counts.ts`: `countAdjacentBears`, `floodReveal`, `listStartCells`; the file is not called `board.ts` because that collides with `Board.tsx` on a case-insensitive filesystem). Game logic (`game.ts`): the state holds one code per square (hidden, revealed, flagged, bear met) plus hints, time and status; revealing a bear shows it and costs one of 3 lives (the third ends the game); flagged squares are never opened, not even by a flood or a chord; chording (pressing a number whose flags and met bears equal it) opens its remaining neighbours, and wrong flags wake bears; Hint asks the solver for a square proved safe from what is open (it works from any state, also after a bear was met, and takes a wrong flag off that square) and costs a point; score is 5 minus bears met and hints, at least 1 for a win, 0 for a loss. UI: `Board.tsx` is a `role="grid"` table of buttons (tap opens or chords, a right click or a 450 ms touch press flags and suppresses the click that follows, F flags, arrows move focus); a mouse never long-presses; `useBearSession.ts` keeps the latest flag mode in a ref so rapid presses work; `Icons.tsx` has the paw and pennant SVGs. Flags and bears are drawn in `--danger`, numerals in `--primary`, `--success-text` and `--danger` (the digit always carries the meaning). On a 320px phone the 11x11 squares are about 23px wide.
- **Weather Window** (`games/weather-window`, finished): a memory and planning game. The week's forecast is shown for a few seconds (`previewSeconds`), then every day is hidden; the player gives each trip its own day from memory and submits once. `catalogue.ts` holds the 5 weathers, 5 trips and the `FIT` table (0 to 3 points per trip and weather; the fit guide is always visible, so the forecast is the only thing to remember). Tiers follow the weekly pattern (`tiers.ts`): easy 5 days and 2 trips with 15 s and 2 peeks, medium 7 days and 3 trips with 10 s and 2 peeks, hard 7 days and 4 trips with 7 s and 1 peek. Puzzles are pre-generated into `puzzles.json` (`{ w: weather per day, t: trips }`; 210 easy, 315 medium, 210 hard) by `npm run weather:build` (about 4 s; seeds start at a fixed base per tier and duplicates are skipped, so a bigger pool keeps the old puzzles); run `npm run weather:verify` after every build. The quality guarantee is `solver.ts` (`analysePuzzle` enumerates every plan): a puzzle is kept only if the best plan is at least 2 points ahead of every plan with different weather (`rival`, so the best plan is clear), the best plan reaches 75% of the maximum, a blind plan averages at most 55% of the best, the forecast has at least 3 kinds of weather, and on medium and hard the trip-by-trip `greedy` plan is worse than the best (planning matters, not only memory). Game logic (`game.ts`): phases intro, memorise, plan, done; the preview starts only when the player presses the button; a state saved during the preview restores as planning (so a reload cannot show the forecast twice); `placeTrip` moves a trip and unplans whoever held the day; `spendPeek` uses a peek; submit wins at 55% or more of the best points; score is the stars from `rateShare` (55% gives 2, 75% gives 3, 90% gives 4, 100% gives 5) minus peeks used, at least 1 for a win, 0 for a loss. UI: `Forecast.tsx` (day cards, disabled outside planning), `Trips.tsx`, `FitGuide.tsx`, `Controls.tsx` (peek arms a mode, submit), `Review.tsx` (your plan next to the best plan; days with the same weather count as a match); `useWeatherSession.ts` keeps the latest selection in a ref so quick taps work and counts the preview down only while the page is visible; a peek shows one day for 2 s. Icons are SVG and every weather and trip also has a text label.

### Content pipeline

Puzzles live in `src/games/mystery-place/puzzles.json`. New puzzles start as drafts in `content/drafts/` with a Wikipedia quote as evidence for every clue. The checker verifies that the quote exists, that numbers match, and that no clue leaks the country name, an alias or the demonym. A weekly GitHub workflow drafts puzzles with an OpenAI-compatible API (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`) and opens a PR for human review. Never merge or hand-edit puzzles without running `content:check`.

## Frontend guidelines

These are the standards for all code here. They extend the user's global conventions; where both speak, the stricter wins. ESLint enforces the mechanical ones.

### Code style

- KISS. The simplest thing that works, no speculative abstraction, no dead code, no duplication.
- **No comments** and no JSDoc. Names and structure carry the meaning. ESLint fails on any comment.
- **No `break` or `continue`.** Use `find`, `some`, `every`, `filter`, early returns or small functions.
- Naming states the action and agrees with the return type. `find*` may return `null`. `get*` expects the value to exist and throws if not. `is*`/`has*` return booleans. `handle*` are event handlers, `on*` are callback props.
- Functions are small and do one thing. Prefer pure functions; pass dependencies as arguments.
- Prefer `const`, immutable updates and early returns over nested conditionals.
- Named exports only. One component per file, file named after it.

### TypeScript

- Strict mode. No `any`; use `unknown` and narrow.
- No non-null assertions (`!`) in production code. They are allowed only in tests and test helpers.
- Model states as discriminated unions (for example `GuessFeedback`), not optional fields plus flags. Make illegal states unrepresentable.
- Parse data at the boundary (JSON, `localStorage`, network) with type guards in `core/guards.ts`, then trust the types inside.
- Use `interface` for props and object shapes, `type` for unions and aliases. Props interfaces are named `<Component>Props`.

### React

- Function components and hooks only.
- Derive values during render instead of mirroring them in state. State holds the minimum.
- `useEffect` is for synchronising with the outside world (DOM, timers, storage). Always return cleanup for timers and listeners. Do not use it to compute values or react to props you could handle in an event.
- Keys are stable ids, never array indexes for reorderable lists.
- Components are presentational where possible; side effects and persistence sit in hooks.
- No prop drilling beyond two levels: compose with `children` or split the component first.
- Use the native `<dialog>` through `ui/Modal`, not custom overlays.

### Accessibility

Treat it as a requirement, not polish. `jsx-a11y` is enforced.

- Real elements first: `button` for actions, `a` for navigation, `dialog` for modals, lists for lists.
- Every interactive control has an accessible name. Icon-only buttons need `aria-label`.
- Everything is keyboard operable with a visible focus ring. The guess input is a proper combobox (`aria-activedescendant`, arrow keys, Enter, Escape).
- Status changes are announced with `aria-live="polite"`. Meaning is never carried by colour alone: pair it with text or an icon.
- Respect `prefers-reduced-motion` for animations and confetti.
- Contrast meets WCAG AA in the tokens, and `src/styles/contrast.test.ts` enforces it in light and dark: text pairs at 4.5:1 and graphics (square borders, focus ring) at 3:1. Use `--success-text` for green text, never `--success`, and `--cell-edge` for borders that identify a control. Colours drawn on the generated scenes are fixed constants (`MARKER_COLOURS`) tested against every scene ground.

### CSS

- Plain CSS with custom properties. Design tokens live in `styles/tokens.css`; never hard-code colours, spacing or radii in a component stylesheet.
- Each component imports its own co-located `.css`. Shared patterns (buttons, cards) go in `styles/primitives.css`.
- Class names are lowercase-hyphenated and prefixed by the component's role to avoid collisions (`guess-badge`, `clue-new`).
- Mobile first. The game must work at 375px width without horizontal scroll, with touch targets of at least 44px.
- Warm outdoorsy look: keep to the existing palette and typography in the tokens.

### Performance

- Static HTML with a single React island per game page. Do not add a client framework router, state library or UI kit.
- Keep the island small. Do not add a dependency for something a few lines of code can do; justify any new package.
- Static assets are inlined or tiny. No images where an icon component or emoji does the job.

### Testing

- Behaviour over implementation: test what a player sees and does, through the DOM, using `@testing-library/react` and `user-event`. Query by role and accessible name first, never by class unless it is the only signal.
- Pure logic gets unit tests next to the file (`x.test.ts`). Components and hooks get `x.test.tsx`. Each game has one integration test that plays the whole flow (win, loss, restore, dialogs).
- Fix time with `vi.useFakeTimers({ toFake: ["Date"] })` when only the date matters. Use full fake timers only for timer behaviour, and drive them with `act`.
- Storage is cleared after every test by `src/testing/setup.ts`. Tests must not depend on order.
- When you add a behaviour test, break the code once to prove the test fails, then revert. A test that cannot fail is worthless.
- Content checks are tested with local fixtures. Tests never touch the network.

### Adding a new game

1. Propose the rules first and wait for approval. Build one part at a time; do not scaffold ahead.
2. Create `src/games/<name>/` with `types.ts`, pure game logic, hooks, components and CSS.
3. Reuse before writing: for a country-guessing game, render `ui/GuessingGame` with a storage, rules and a `renderStage` for the game's own view. Otherwise reuse `core/daily.ts`, `core/gameStorage.ts`, `core/streak.ts`, `hooks/`, `ui/Modal`, `ui/ShareButton` and `ui/StatsSummary`.
4. Add a page in `src/pages/`, a card on the home page, and a share text builder.
5. Add unit tests, component tests and an integration test before calling it done.
